# Волна 2: Доступность, клавиатура и первый экран — план реализации

**Цель:** сделать приложение управляемым с клавиатуры и понятным скринридеру,
и заменить пустой первый экран блоком быстрого старта.

**Подход:** строка списка перестаёт быть `div` с обработчиком и становится настоящей
кнопкой, а действия переезжают наружу этой кнопки. Имена кнопок переносятся из `title`
в доступное имя. Оверлеи получают удержание и возврат фокуса. Появляется вежливый
регион объявлений для генерации.

**Ограничения:** без сборки и зависимостей. WebSocket/SSE, `_handoffStreaming`,
`resumeSSE` и сторож стриминга не трогаются. Разметка меняется только там, где это
описано ниже. Откат — из `C:/Temp/claude/wave2-backup-*`.

**Спека:** отчёт «Редизайн TaleEngine», волна 2.

## Глобальные ограничения

- Вложенных интерактивных элементов внутри кнопки быть не должно: действия строки
  становятся соседями кнопки, а не её потомками (WCAG 4.1.2).
- Внутри `<button>` допустим только фразовый контент: все `div` в строках становятся `span`.
- Скрытие содержимого не должно оставлять его в порядке табуляции (WCAG 2.4.3).
- Объявляется ЗАВЕРШЁННЫЙ ответ, а не каждый токен: иначе речь перезапускается
  десятки раз в секунду.
- Ни одно изменение не должно затронуть счётчики методов стриминга.

## Задача 1: Строка списка становится кнопкой

**Файлы:** `frontend/app.js:2894-2909` (персонажи), `:2925-2949` (чаты),
`:2960-2975` (группы), `:2983-2991` (расшаренные); `frontend/styles.css`

**Что не так:** строка это `<div @click>`. Пользователь клавиатуры может удалить чат,
но не может его открыть, потому что кнопки действий внутри строки настоящие, а сама
строка нет.

**Почему не `role="button"` на `div`:** внутри строки лежат кнопки действий, а
интерактивный элемент внутри элемента с ролью кнопки недопустим. Поэтому строка
раскладывается на два узла: кнопка содержимого и соседний блок действий.

- [x] **Шаг 1.** В каждой из четырёх строк содержимое заворачивается в
      `<button type="button" class="row-main">`, действия остаются снаружи неё.
- [x] **Шаг 2.** Все `div` внутри новой кнопки заменяются на `span`
      (`.avatar`, `.grow`, `.row-text`, `.row-title`, `.row-sub`).
- [x] **Шаг 3.** Кнопка получает `aria-label` с полным смыслом строки (имя, признак
      закрепления, признак нового ответа) и `aria-current="true"` у открытой.
- [x] **Шаг 4.** Действия групп заворачиваются в `.row-actions`, как у чатов: сейчас
      четыре кнопки видны всегда и съедают ширину названия.
- [x] **Шаг 5.** CSS: `.row-main` получает скин строки вместо скина кнопки, отступы
      переезжают в неё из `.list-item`, гасятся `button:active { transform }` и
      `button:hover { border-color }`, фокус рисуется внутрь.
- [x] **Шаг 6.** Проверить: `node --check`, число `<button` выросло ровно на 4
      (по одной кнопке-строке на список).

## Задача 4: Фокус-ловушка и возврат фокуса

**Файлы:** `frontend/app.js`

**Что не так:** ни одной ловушки. Дровер стоит в шаблоне после ленты, поэтому дойти
до него клавиатурой значит протабать весь чат. При закрытии фокус уезжает в начало
документа.

**Почему без `ref` на каждый оверлей:** оверлеев десять, и добавление `ref` каждому
это десять правок разметки ради того, что решается одним запросом к DOM. Порядок
слоёв уже задан порядком в шаблоне: дровер раньше модалок, диалог последним.

- [x] **Шаг 1.** Метод `_topOverlay()` возвращает последний в DOM видимый
      `.drawer, .modal` — это и есть верхний слой.
- [x] **Шаг 2.** Глобальный обработчик `keydown` на Tab: если оверлей открыт,
      фокус циклится внутри него.
- [x] **Шаг 3.** Watcher на признак «какой-то оверлей открыт»: при открытии
      запоминается `document.activeElement` и фокус уходит внутрь оверлея,
      при закрытии возвращается на запомненный элемент.
- [x] **Шаг 4.** Оверлеи получают `role="dialog"` и `aria-modal="true"`.
