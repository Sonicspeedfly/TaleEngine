# Подсистема памяти Horae

Horae — система памяти/контекста. Она совмещает две идеи SillyTavern:

- **World Info** — записи срабатывают, когда в недавнем тексте встречаются их
  **ключевые слова** (`keywords`).
- **Снимки состояния** — записи с `always_on=True` подмешиваются **всегда** (инвентарь,
  скрытые характеристики, текущее положение сюжета, описание сцены).

Плюс автоматическая **долгая память** для длинных чатов (см. «Три слоя памяти»
ниже): активное окно дословной переписки, мастер-снимок старой части чата и
атомарные факты, которые вспоминаются по смыслу текущей реплики.

Код: `backend/horae_memory.py` (сборка контекста), `backend/horae_recall.py`
(окно, факты, поиск), `backend/hierarchical_memory.py` (ядро мастер-снимка:
пакеты, слияние, проверка ответа, сжатие), `backend/memory_service.py` (снимок в
БД, ежеходный проход, задания пересборки, статус, сброс, экспорт) и тонкие
обёртки `backend/main.py::_maybe_update_summary` / `_summary_pass`.
Модели: `HoraeEntry`, `HoraeFact` (см. [DATA_MODEL.md](DATA_MODEL.md)).

## Области видимости записи

Запись Horae может быть привязана так:

| `session_id` | `character_id` | Смысл |
|:---:|:---:|---|
| NULL | NULL | **Глобальный лор мира** — виден во всех чатах (и всем пользователям) |
| задан | — | **Память конкретного чата** (приватная для владельца чата) |
| — | задан | **Лорбук персонажа** — применяется в чатах с этим персонажем |

В UI у каждой записи показывается тег области (🌐 глоб. / 💬 чат / 🎭 перс.).

## Как собирается контекст

`assemble_context(...)` — **чистая** функция (без БД и сети, поэтому легко покрывается
юнит-тестами `tests/test_horae_memory.py`). Порядок:

1. **Триггеры.** По тексту текущего сообщения + хвоста истории ищутся записи, чьи
   `keywords` встретились (`_scan_text_for_triggers`). `always_on`-записи добавляются
   безусловно.
2. **Системный промпт (начало)** = паспорт персонажа (`system_prompt/description/
   personality/scenario/mes_example`) + блок персоны пользователя + блок сработавших
   записей Horae (по `priority`, КРОМЕ авто-сводки) + `BEHAVIOR_GUIDE` (роль, работа
   с файлами, анти-выдумки) + `STYLE_GUIDE` (портативная разметка).
2b. **Переинъекция в КОНЕЦ** (сильнейшая позиция — recency bias). Чтобы характер не
   «плыл» и память реально влияла в длинном окне, прямо перед репликой пользователя
   добавляются системные блоки: `[ХРОНИКА И СОСТОЯНИЕ ЧАТА]` (мастер-снимок Horae),
   `[HORAE RECALLED MEMORY: …]` (вспомненные факты, если есть), манифест
   приложенных файлов, инструкция веб-поиска (если включён), время пользователя,
   Author's Note, **якорь характера** (`_render_char_anchor`) и, в самом конце,
   **Post-History Instructions** персонажа (SillyTavern «jailbreak»/UJB).
3. **Бюджет токенов.** Несжимаемая часть — системный промпт + текущее сообщение.
   История добавляется с конца (свежие важнее), пока хватает окна контекста:
   `params.context_tokens` из UI (Генерация → «Окно контекста») либо
   `CONTEXT_TOKEN_BUDGET` из .env (по умолчанию 200 000: у Gemini вход свыше
   ~200 тыс. токенов тарифицируется вдвое дороже целиком).
   Вложения истории (фото/аудио/видео) пересылаются модели заново: по умолчанию
   ВСЕ (полная память), опционально — до N МБ на ход (`history_files_mb` из UI
   «Файлы в памяти диалога» / `HISTORY_FILES_MB` из .env; не влезшие заменяются
   пометкой `[видео: имя]`). Данные достаются точечно из blob-таблицы.
4. **Author's Note** добавляется отдельным system-сообщением в самый конец контекста —
   так у заметки максимальное влияние на ответ.
5. **Аватары** (если включено `send_avatars`) — внешность персонажа и пользователя
   подмешиваются как картинки.

`build_context_from_db(...)` — обёртка: читает персонажа, персону, историю и записи
Horae (свои + лорбук персонажа, с учётом доступа), применяет долгую память
(`_long_memory`: срез активного окна + поиск фактов) и зовёт `assemble_context`.
Вызывающий, который передаёт историю сам (regenerate/continue/retry), передаёт и
`history_ids`; без них id не угадываются — окно ничего не выбрасывает и факты не
отсеиваются.

## Приватность

`GET /api/horae` и операции над записями скоупятся по доступу (`_can_access_horae` в
`main.py`): глобальный лор виден всем; приватная память чата и лорбук персонажа — только
владельцу, админу и соавтору расшаренного чата. Регрессия закреплена тестом
`tests/test_horae_privacy.py`.

## Откуда берутся записи

- Вручную в UI (вкладка «Память Horae»): заголовок, содержимое, ключевые слова,
  категория, `always_on`, область (глобально / только этот чат).
- При **импорте чата** (нативном или SillyTavern) — снимок состояния и хронология
  событий (см. [IMPORT_EXPORT.md](IMPORT_EXPORT.md)).
- При **импорте карточки персонажа** — лорбук (`character_book`) → записи персонажа.


## Три слоя памяти

Проблема: в длинном чате (вплоть до ~1M токенов) модель получала всю переписку,
насколько хватало бюджета, и тонула в ней (Context Dilution). Факты и хронология
из начала размывались сотнями реплик, а не влезшее в бюджет просто отрезалось.
Поэтому история перед сборкой контекста проходит конвейер из трёх слоёв.

В терминах уровней контекста: Tier 1 — системный промпт, персонаж, правила и
якоря; Tier 2 — мастер-снимок всей старой истории (плюс вспомненные факты);
Tier 3 — активное окно, последние сообщения дословно. В этой разбивке ход
показывает монитор токенов (см. ниже).

### 1. Активное окно (дословно)

Последние `DEFAULT_WINDOW = 50` сообщений идут в модель без изменений
(`horae_recall.window_start`; сама функция живёт в `hierarchical_memory`, а
`horae_recall` её реэкспортирует). Всё старше выбрасывается, **но только если уже
учтено снимком** (id сообщения ≤ указателя «учтено до»): пока снимок догоняет
длинный или импортированный чат, модель видит историю целиком. Отбрасывается
только ведущий непрерывный отрезок учтённых сообщений; первое неучтённое или
сообщение без id останавливает срез.

Граница окна двигается шагом `WINDOW_STEP = 4`, а не на каждом ходу: иначе
каждый ход сдвигал бы начало промпта и ломал кэш промпта провайдера. Поэтому
дословно идут 50–53 сообщения.

Размер окна — вкладка «Память» → «Активное окно» (`/settings/ui`, ключ
`memory_window`; любое целое 0–1000, кнопки 20/50/80/150/«вся история», `0` =
окно выключено, история целиком). До 2.5.0 окно было 20: сохранённое значение 20
один раз поднимается до 50 при загрузке интерфейса (флаг `memory_defaults_v: 2`
в настройках `ui`), а выставленное после этого вручную 20 больше не трогается.
Указатель берётся только у снимка, который реально идёт в контекст (`enabled` и
`always_on`): если снять с него «всегда», окно ничего не выбрасывает.

### 2. Мастер-снимок (скользящая хроника)

После каждого хода запускается фоновая задача `main.py::_maybe_update_summary`
(внутри — `memory_service.run_incremental`). Когда старше активного окна
накопилось `summary_every` новых сообщений (по умолчанию 10, `AUTO_SUMMARY_EVERY`
в .env; в UI — 6/10/20), модель вливает их в **мастер-снимок**:
`снимок_N = слияние(снимок_{N−1}, пакет_N)`. Снимок — Markdown строгой схемы из
четырёх разделов: хроника, персонажи со статусами, реестр фактов и лора, списки.
Как он собирается и проверяется — в разделе «Мастер-снимок и пакетная
пересборка» ниже.

- Сообщения из активного окна в снимок не берутся: свайпы, «Продолжить» и правки
  свежих ответов попадают в память уже в окончательном виде.
- Бэклог режется на пакеты до `MEMORY_BATCH_SIZE = 20` сообщений и
  `MEMORY_BATCH_CHARS = 80 000` символов, за ход — не больше
  `MEMORY_MAX_BATCHES_PER_TURN = 6` пакетов (в `main.py` остались прежние имена
  `_SUMMARY_CHUNK_CHARS` и `_SUMMARY_MAX_CHUNKS` — псевдонимы этих настроек).
  Сообщение идёт в пакет целиком, а длиннее бюджета пакета — началом и концом с
  пометкой `[…середина длинного сообщения пропущена…]`: целиком оно превысило бы
  окно быстрой модели, и сводка падала бы на каждом ходу. Указатель двигается
  только за тем, что модель действительно видела. Весь бэклог разом сворачивает
  кнопка «Догнать».
- Фоновые вызовы идут на `summary_model` из подключения (пусто = модель чата), но
  остаются служебными — `params=None`, фильтры безопасности выключены. Иначе на
  жёстком ролевом эпизоде провайдер блокировал сводку, и память молча замирала.
  Свои температура (`MEMORY_TEMPERATURE = 0.2`) и длина вывода задаются через
  `llm_gateway.sampling_overrides`, не трогая сигнатуру `complete`: снимок
  переписывается целиком, и обычного `max_tokens` ответа чата на него не хватает.
  Потолок вывода — `max(DEFAULT_MAX_TOKENS, round(бюджет снимка × 1,4) + 1024)`,
  при бюджете 12 000 — 17 824 токена, но не больше лимита вывода модели памяти,
  если его знает LiteLLM (см. «Настройки»).
- Результат — запись Horae этого чата: категория `summary`, заголовок
  «📜 Память чата (авто)», `always_on=True`, `priority=50`, ключевое слово
  `__auto__`. Указатель «учтено до» хранится в `meta.last_message_id` вместе с
  версией формата `meta.v = 2` (`horae_recall.SUMMARY_FORMAT`) — в 2.5.0 они не
  изменились. Рядом лежат `meta.schema = "hms-1"` (снимок новой схемы),
  `meta.tokens` (размер), `meta.updated_by` (`incremental`, `catchup` или
  `rebuild`), `meta.warnings` (последние пять предупреждений), `meta.facts_upto`
  (до какого сообщения разобраны факты), `meta.last_error` (сбой ежеходного
  прохода, см. ниже) и буфер пересборки `meta.rebuild`. **Текст не
  режется**: до 2.5.0 `_adopt_summary` сохранял только первые 6000 символов, и
  хвостовые разделы (персонажи, списки) пропадали молча. Запись видна во вкладке
  «Память»; её можно править руками или удалить (снимок начнётся заново). Правку
  возьмёт за основу следующий пакет, если она сохранена до его начала и буфера
  пересборки нет. Правку, сделанную, пока модель считает пакет или идёт
  пересборка, код не защищает (см. «Свёртка пакетами»): править стоит, когда
  задания и буфера пересборки нет.
- **Сводка до 2.4.0 пересобирается.** Старый сводчик резал реплики до 1500
  символов, а бэклог — до первых 24 000, но ставил указатель на последнее
  сообщение. Окно верит только указателю с `v = 2`
  (`horae_recall.trusted_pointer`), поэтому у старой сводки оно не выбрасывает
  ничего — история идёт как до обновления. Новый сводчик пересобирает память с
  нуля в `meta.rebuild = {content, last_message_id}` (заодно извлекая факты из
  всей старой истории), а в контекст до конца пересборки идёт старая сводка.
  Подмена (`_adopt_summary`) — только когда пересборка догнала бэклог (остаток
  меньше `summary_every`); по указателю старой сводки не подменяем — у сводки
  из импорта его нет. Разово это стоит пересказа всей переписки чата — задайте
  дешёвую `summary_model` до обновления. Ручные правки старой авто-сводки в
  новую не переносятся: храните свои заметки отдельной записью памяти.
- **Сводка 2.4.x (свободный пересказ с `v = 2`) не пересобирается.** Её указателю
  окно верит, а ближайший проход сливает пересказ с новым пакетом в снимок новой
  схемы: слияние принимает любое предыдущее состояние, а проверка «сдувания» для
  несхемного снимка отключена. Чистая конвертация — «Пересобрать с нуля».
- Факты извлекаются только из сообщений новее уже разобранных — наибольшего из
  `max(source_message_id)` фактов чата и отметки `meta.facts_upto` (её двигает
  каждый удачный разбор, даже без единого факта): снимок, начатый заново
  (удалили запись, пересборка), не плодит дубли. Снимок пакета записывается ДО
  запроса фактов; если ответ модели фактов не пришёл (сбой, «Остановить»,
  остановка сервера), отметка стоит, и следующий пакет доизвлекает пропуск
  вместе со своими сообщениями — не больше двух пакетов назад и в пределах
  бюджета пакета (свежие строки важнее).
- **Сбой ежеходного прохода** (ошибка API после повторов, снимок не по схеме,
  обрыв лимитом вывода) пишется в `meta.last_error = {message, kind, at,
  failures}` — у чата без записи снимка в памяти процесса. Следующий
  ежеходный проход ждёт `min(6 ч, 10 мин · 2^(failures − 1))` от `at`: 10 мин,
  20, 40… Раньше каждый ход повторял тот же платный провал (обрыв — три
  полноразмерных запроса за ход), а видно его было только в логе. Удачная
  запись снимка (любым путём) ошибку убирает; «Догнать» и «Пересобрать с нуля»
  паузу не ждут. Вкладка «Память» показывает ошибку и время следующей попытки.
- Перед записью пакета кусок сверяется с чатом: если его сообщения переписали
  или удалили, пока модель считала (а id занял новый ответ), пакет не
  записывается — иначе указатель лёг бы на невиданный текст. Ежеходный проход
  начнёт этот кусок заново на следующем ходу; задание собирает пакет заново сразу,
  но не больше трёх отказов подряд.
- В контекст снимок идёт блоком `[ХРОНИКА И СОСТОЯНИЕ ЧАТА]` у конца, рядом с
  репликой пользователя: когда окно отрезает старую переписку, это единственное,
  что от неё остаётся. Снимок новой схемы идёт телом блока как есть, после строки
  «Мастер-снимок старой части чата; последние сообщения выше идут дословно.»;
  другие записи категории `summary` — ниже, под «Дополнительные записи памяти:».
  Старый свободный пересказ — строкой `- заголовок: текст`, как раньше.
- Удалили свежие сообщения — `_clamp_summary_pointer` прижимает указатель (и
  указатель буфера пересборки) к последнему оставшемуся сообщению, а не в ноль,
  что заставляло пересказывать весь чат заново, и удаляет факты из удалённого.
  id в SQLite переиспользуются, поэтому без этого новый ответ с «чужим» id
  считался бы уже учтённым.
- Выключатель: «Память» → «Авто-сводка сюжета» (`auto_summary`). Выключен —
  ежеходный проход не идёт, указатель не растёт, и окно ничего не выбрасывает. На
  ручные задания («Пересобрать с нуля», «Догнать») выключатель не влияет.

### 3. Атомарные факты (`backend/horae_recall.py`, таблица `horae_facts`)

В тот же фоновый проход модель выписывает из пакета переписки атомарные факты
(`FACTS_PROMPT`): одно утверждение, имена вместо местоимений, только то, что прямо
сказано, до `MAX_FACTS_PER_CHUNK = 20` фактов по `MAX_FACT_CHARS = 300` символов.
Запрос идёт через тот же менеджер, что и слияние: пауза между запросами и повторы
при сбоях у них общие. Индексируются именно факты, а не сырые реплики: вектор
абзаца ролевого чата «про всё сразу» и похож на всё понемногу.

`store_facts` отбрасывает точные повторы, а при заданной модели эмбеддингов — и
почти повторы (косинус ≥ `DUP_COSINE = 0.95` среди последних 400 векторов).
Сбой записи фактов не откатывает уже сохранённый снимок.

**Поиск** (`recall`, на каждом ходу). Запрос — реплика пользователя; хвост
разговора (две последние реплики) идёт отдельно и сам по себе факт не вспоминает,
только помогает с «а что с ним?».

- **По смыслу**, если задана `embedding_model`: косинус с порогом
  `SIM_THRESHOLD = 0.75`. Включается, только когда векторы текущей модели есть
  у ≥ 95% фактов (`VECTOR_COVERAGE`); до тех пор — поиск по словам, а векторы
  досчитываются после каждого хода пачками по 50 (не больше 10 пачек за раз).
- **По словам** (режим по умолчанию): основы слов с учётом падежей и глагольных
  приставок, IDF по фактам этого чата, вес `ENTITY_BOOST = 2.5` для имён
  (слово с заглавной внутри предложения), порог `LEXICAL_THRESHOLD = 0.2`.
  Слово, которое есть в ≥ 25% фактов чата (и не меньше чем в трёх), само по себе
  совпадением не считается — иначе «ок» или «иду дальше» вспоминали бы факты про
  главных героев на каждом ходу. Совпадения только с хвостом весят 0,3.
- Порог применяется к сходству, ранжирование — по «сходство × свежесть», где
  свежесть = 0,5 + 0,5 · 0,5^(возраст / 300): полураспад 300 сообщений ЭТОГО
  чата, пол 0,5 — старые факты ослабляются, но не обнуляются.
- В контекст идут не больше `TOP_K = 5` фактов, и только из сообщений, которых
  модель не видит дословно (отсев — после обрезки истории по бюджету, так что
  при `memory_window = 0` факты из срезанного бюджетом тоже вспоминаются).
  Блок `[HORAE RECALLED MEMORY: …]` стоит у конца, факты — в порядке чата.
  **Нет похожих — нет и блока**: пустой или натянутый блок памяти модель охотно
  «дополняет» выдумкой.

Эмбеддинги считает `llm_gateway.embed` через тот же маршрут, что и чат (прокси
или напрямую), с таймаутом 10 с; расход пишется в статистику как `embedding`.
Выключатель фактов: «Память» → «Факты» (`horae_facts`, выключены только явным
`false`). Групповые чаты тоже получают блок фактов (`group_chat._group_recalled`),
но активного окна у них нет — история там режется только бюджетом.

## Мастер-снимок и пакетная пересборка (2.5.0)

До 2.5.0 средний слой был свободным конспектом из пяти разделов: не больше
шести кусков за ход и только после ответа ассистента, без пауз, повторов и
прогресса. `_adopt_summary` обрезал готовую сводку до 6000 символов, хвостовые
разделы пропадали молча, и модель «забывала» персонажей и договорённости из
начала чата. Большой бэклог (импорт) догонялся за несколько ходов, и пересобрать
память вручную было нельзя.

Теперь это свёртка по пакетам в снимок строгой схемы. Чистое ядро —
`backend/hierarchical_memory.py` (только stdlib: ни БД, ни FastAPI, ни litellm;
модель — колбэк), поэтому весь его контракт проверяется тестами без сети
(`tests/test_hierarchical_memory.py`). Адаптер к БД — `backend/memory_service.py`:
источник пакетов, запись снимка и буфера, задания, статус, сброс, экспорт. Один
движок и один промпт — и для ежеходного прохода, и для полной пересборки.

Физически снимок стоит в хвосте промпта (после окна, перед репликой
пользователя), а не между системным промптом и окном: иначе каждое обновление
снимка сбрасывало бы кэш промпта провайдера для всей истории.

### Схема снимка

Четыре раздела с фиксированными заголовками (`hierarchical_memory.SECTIONS`):

```
## [ХРОНИКА И СОБЫТИЙНЫЙ КАРКАС]
- [#a–#b] (время сюжета, если известно) кто → что → результат/решение
## [АКТИВНЫЕ ПЕРСОНАЖИ И ИХ СТАТУСЫ]
- Имя — здоровье: …; локация: …; психологический вектор: …; скрытые мотивы: …; при себе: …; отношения: …
## [ФАКТОЛОГИЧЕСКИЙ РЕЕСТР И ЛОР]
- Сущность — что это / правило / решение (#id)
## [СПИСКИ И МЕДИА-АНКОРЫ]
### Название списка
- элемент — значение/роль (#id)
```

- Markdown, а не JSON: модель надёжно пишет Markdown, его читает человек во
  вкладке «Память» и в экспорте, в контекст он идёт как есть. Пустой раздел —
  заголовок и строка «—».
- Разбор (`parse_sections`) прощает оформление: `## [ИМЯ]`, `### ИМЯ`, `[ИМЯ]`,
  жирный заголовок; регистр и ё/е не важны. Записывается канонический вид
  (`render_snapshot`): `## [ИМЯ]` в порядке схемы.
- Снимок «структурирован» (`is_structured`), если в нём есть хотя бы три из
  четырёх заголовков. По этому признаку решается, как снимок идёт в контекст,
  охраняет ли его страж и пишет ли вкладка «старая схема — пересоберите».
- Промпт слияния (`MASTER_STATE_PROMPT`) требует: `[Текущая память]` — только для
  чтения, всё, чего новый блок не касается, переносится дословно; только то, что
  прямо сказано, неясное — «(?)», время не указано — «время не указано»; имена,
  числа и цитаты — символ в символ; записи разделов 2–4 не исчезают (изменилось —
  обновить на месте с прежним значением в скобках, утратило силу — «(неактуально
  с #id: причина)»); хроника дописывается в конец, каждая запись — с диапазоном
  `[#a–#b]`; бытовые реплики без последствий не записываются, необратимые решения,
  договоры и передача важных предметов — всегда.

### Свёртка пакетами

Каждое сообщение превращается в строку пакета (`normalize_message`):

```
[#1234 · 2026-09-20 14:03 · Эльвира] текст реплики
📎 изображение «map.png»; аудио «voice.ogg»
```

- Автор — настоящее имя: реплики пользователя — персона чата (иначе
  «Пользователь»), ответы — `speaker_name` (групповой чат), иначе персонаж чата
  (иначе «Персонаж»), системные — «Система». Время — в часовом поясе чата; пояс
  не задан или не разобрался — UTC.
- Из текста вырезаются data:-URI, сплошной base64 от 200 символов, `<think>` и
  `<thinking>`, `<style>`, `<script>`, HTML-комментарии и zero-width символы;
  известные HTML-теги снимаются с сохранением текста. Только известные: ремарки
  вроде `<OOC: …>` или `<time skip>` остаются текстом. Markdown и блоки кода не
  трогаются.
- Вложения — подписью по типу и именем файла. Что внутри файла, модель узнаёт из
  текста реплик — обычно из ответа ассистента, разбирающего файл. Обычно он в
  том же пакете, но не обязательно: сообщение с файлом может быть последним в
  пакете или последним перед окном, и тогда разбор попадёт в следующий пакет.
  Сообщение без текста и без вложений в пакет не попадает. Сообщение, от
  которого после чистки ничего не осталось (одни `<think>`), идёт в пакет без
  строки: модель его не видит, но указатель его проходит.
- Пакет (`plan_batch`) — подряд до `batch_size` сообщений, пока строки через
  пустую строку не длиннее `MEMORY_BATCH_CHARS`; хотя бы одно сообщение всегда.
  Пакеты не пересекаются.
- Запрос слияния: системное сообщение `MASTER_STATE_PROMPT`, пользовательское —
  `[Текущая память]` (снимок или `(пока пусто)`) и `[Новые события #a–#b]`
  (строки пакета). Запрос пакета N несёт снимок после пакета N−1 — в этом вся
  свёртка (`scan_and_compress_history`).
- Готовый пакет сразу записывается (`DbBatchSource.commit`), поэтому остановка,
  лимит ежеходного прохода или ошибка сделанного не теряют. Перед каждым пакетом
  цель перечитывается из БД (`DbBatchSource.current_state`), но ручную правку
  снимка во вкладке «Память» это защищает не всегда:
  - «Догнать» и ежеходный проход: правка, сохранённая между пакетами или между
    проходами, становится основой следующего пакета. Правку, сохранённую, пока
    модель считает пакет (десятки секунд, с повторами — минуты), перезапишет
    снимок этого пакета: `commit` не сверяет запись с тем, что прочитал перед
    вызовом модели. Ежеходный проход идёт в фоне сразу после ответа.
  - Пока есть буфер пересборки (`meta.rebuild`: «Пересобрать с нуля», пересборка,
    прерванная ошибкой или перезапуском сервера, сводка до 2.4.0), пакеты читают и
    пишут буфер, а не живую запись. Подмена в конце целиком заменяет живой снимок
    буфером, и правка, сделанная за это время, пропадает без предупреждения.
    Исключение — пересборка, остановленная кнопкой (`meta.rebuild.paused`): её
    буфер ждёт «Продолжить», а все остальные прогоны пишут в живой снимок.

  Интерфейс правку во время задания не блокирует. Править снимок безопасно, когда
  задания и буфера пересборки нет.

### Пауза и повторы

Все запросы прогона — слияние, факты, сжатие — идут через одну «дверь»
(`HierarchicalMemoryManager.call`):

- **Пауза-ограничитель** `MEMORY_DELAY_MS` (1500 мс; поле «Пауза между запросами»)
  от конца предыдущего запроса до следующего: провайдер режет частоту по всем
  запросам ключа. У пакета с фактами две паузы — перед слиянием и перед фактами.
  Пауза действует внутри одного прогона, поэтому задания памяти идут по одному
  на процесс (остальные ждут в очереди, `queued`): пять «Пересобрать» подряд
  иначе давали около трёх запросов в секунду на общий ключ.
- **Классификация ошибок** (`classify_error` — по имени класса исключения,
  HTTP-статусу и тексту ошибки шлюза; ядро не импортирует litellm):

  | Вид | Признак | Повтор |
  |---|---|:---:|
  | `rate_limit` | 429, `RateLimitError` | да |
  | `timeout` | 408, `Timeout`, `APITimeoutError`, `TimeoutError` | да |
  | `server` | 5xx, `InternalServerError`, `ServiceUnavailableError`, `BadGatewayError` | да |
  | `network` | `APIConnectionError`, `ConnectionError`, `OSError` | да |
  | `auth` | 401/403, `AuthenticationError`, `PermissionDeniedError` | нет |
  | `bad_request` | 400/404/422, `BadRequestError`, `NotFoundError`, `UnprocessableEntityError`, `ContextWindowExceededError` | нет |
  | `blocked` | `ContentPolicyViolationError`; пустой ответ с `finish_reason` SAFETY, PROHIBITED_CONTENT, BLOCKLIST, SPII, RECITATION и т. п. | нет |
  | `length` | ответ оборван лимитом вывода: пустой ответ с `finish_reason` LENGTH / MAX_TOKENS, непустой с `finish_reason` `length`/`max_tokens` (шлюз сообщает его через `llm_gateway.finish_reason_probe`) или открытая обёртка без закрытия | нет — сжатие хроники и повтор слияния |
  | `empty` | прочий «ПУСТОЙ ответ» шлюза | да |
  | `unknown` | всё остальное | да |

- **Повтор** — через `min(60, 2 · 2^попытка)` с (2, 4, 8, 16 с), но не меньше
  `Retry-After` провайдера (потолок 300 с) и не меньше паузы; до
  `MEMORY_MAX_RETRIES = 4` повторов, затем ошибка наверх с русским текстом для
  статуса. Отмену задания (`asyncio.CancelledError`) повтор не перехватывает
  никогда. LiteLLM внутри повторяет сам (`LLM_NUM_RETRIES`) — это внешний контур с
  длинными паузами поверх него.
- **Остановка прерывает паузы.** «Остановить» и «Сбросить память» не ждут конца
  паузы между запросами и паузы перед повтором (по `Retry-After` — до 300 с, до
  четырёх раз на запрос): пауза обрывается сразу, и новых платных запросов после
  неё нет (`MemoryCancelled`). Уже начатый запрос к модели доводится — он оплачен.

### Проверка ответа и страж записей

Ответ модели проверяет `validate_snapshot`. Вырезаются `<think>` и ограждения
```` ``` ````; из обёртки `<master_state>…</master_state>` берётся снимок, без
обёртки — весь текст.

**Обрыв лимитом вывода — не брак, а `length`.** Обёртка открыта, но не закрыта,
или шлюз сообщил `finish_reason` `length`/`max_tokens` у непустого ответа: в нём
нет хвостовых разделов — тех самых списков и реестра, что раньше терялись.
Корректирующий ход с тем же лимитом оборвался бы снова (раньше так и было — три
полноразмерных платных запроса и отказ на каждом ходу), поэтому слияние сразу
уходит на путь `length`: сжатие хроники с арками и один повтор (см. «Сжатие
хроники в арки»). Ответ фактов, оборванный лимитом, принимается как есть:
обрывок списка фактов полезен.

Брак:

- пустой ответ; нет раздела; снимок длиннее `max(200 000, 8 × бюджет снимка)`
  символов (порог растёт с бюджетом: русский текст — около 1,9 символа на
  токен, и при бюджете больше ~100 тыс. токенов снимок в пределах бюджета
  отвергался бы);
- «сдувание»: предыдущий снимок структурирован и весит от 800 токенов, а новый
  меньше половины его. Для несхемного предыдущего состояния (пересказ 2.4.x или
  пустая память) проверка не делается — это конвертация.

Брак возвращается модели корректирующим ходом: её сырой ответ и «Ответ отклонён:
<проблемы>. Верни ПОЛНЫЙ снимок заново строго по схеме…», до двух раз. Не
исправила — `SnapshotValidationError`: в память ничего не пишется, указатель не
двигается.

**Страж записей** (`guard_entries`) — детерминированная гарантия для разделов
2–4. Промпт требует переносить записи дословно, но при десятках слияний подряд
модель рано или поздно тихо роняет хвост списка или персонажа второго плана.

- Запись — строка списка верхнего уровня (`- `, `* `, `• `, `1. `) с
  продолжением; в разделе списков запись принадлежит своему подзаголовку `###`.
- Ключ — текст до первого « — » (или « – », « - »), «:», «|» или «(»: регистр,
  ё/е и пунктуация не важны. Запись сохранена, если в том же разделе нового
  снимка есть тот же ключ или похожий (Жаккар по словам ≥ 0,6: «Орден Зари» →
  «Тайный орден Зари» — та же запись). Обновлённая на месте запись не
  дублируется.
- Сопоставление — мультимножество: одна запись нового снимка покрывает одну
  запись старого. Сначала точные совпадения, потом похожие (из свободных —
  самая похожая). Для ключей, которые в старом разделе повторяются, сравнивается
  расширенный ключ — вся первая строка без хвостовых «(#id)»/«(было: …)». Иначе
  записи с одним ключом прикрывали друг друга: «Linkin Park — «In the End»»
  пропадал молча, пока в списке оставался «Linkin Park — «Numb»», как и
  «Кольцо (золотое)» рядом с «Кольцом (серебряным)». Лишний возврат (модель
  слила две записи в одну строку) безопаснее потери.
- Пропавшая запись дописывается исходным текстом в конец своего раздела (в свой
  подсписок, при нужде созданный заново), а в предупреждения (`warnings` статуса)
  — «модель потеряла N записей — возвращены из предыдущего снимка».
- Хронику страж не охраняет: её законно сокращает сжатие в арки.

### Сжатие хроники в арки

Снимок больше бюджета (`MEMORY_SNAPSHOT_TOKENS = 12 000`; поле «Бюджет снимка»)
сжимается (`compact`, `COMPACT_PROMPT`): модель сокращает **только хронику** —
объединяет старые записи в арки `- [#a–#b] Арка «название»: суть, ключевые
решения, последствия`, последние 12 записей оставляет как есть, разделы 2–4
переносит дословно.

- Цель в промпте — 80% бюджета (9 600 токенов при 12 000): снимок, сжатый ровно
  до бюджета, превысил бы его уже на следующем пакете, и сжатие шло бы каждый раз.
- Модель зовётся, только когда накопилось что сворачивать — от шести записей
  старше последних двенадцати, не считая уже готовых арок. До тех пор снимок
  остаётся больше бюджета, а сжатие не тратит запрос ради одной записи.
- Ответ проходит ту же проверку (без «сдувания»), но из него берётся **только
  хроника**; разделы 2–4 остаются из входного снимка символ в символ. Раньше
  ответ шёл в снимок целиком, а страж сверяет лишь ключи записей: модель
  сворачивала хронику и «заодно» ужимала «Эльвира — здоровье: …; при себе: ключ
  №7…; скрытые мотивы: ищет брата» до «Эльвира — ранена», и это принималось
  молча.
- Нижняя граница: пустая хроника в ответе или хроника без самой свежей записи
  (её последний номер сообщения `#b` обязан остаться — в записи или концом
  арки) — отказ: «сжатие вернуло пустую хронику / потеряло последние записи
  хроники (#N) — оставлен прежний снимок». Хроника не стала короче или сжатие
  не удалось — тоже предупреждение и прежний снимок.
- Разделы 2–4 не сжимаются никогда. Если бюджет превышают они сами, снимок
  остаётся больше бюджета, а в предупреждениях — «снимок превышает бюджет: X из Y
  токенов (хроника уже сжата; реестр и списки не сжимаются автоматически)».
  Когда следующее сжатие вернуло снимок в бюджет, это предупреждение из итога
  прогона убирается.
- Ответ слияния упёрся в лимит вывода (`length`): снимок сжимается с разрешением
  сворачивать и старые арки в арку более высокого уровня (`COMPACT_ARCS_PROMPT`),
  затем слияние повторяется; повторный обрыв — ошибка «Ответ модели упёрся в
  лимит длины вывода: …».
- **Снимок и лимит вывода.** Модель переписывает снимок целиком, поэтому до
  слияния он сверяется с лимитом вывода модели памяти (`MemoryConfig.output_tokens`
  — её `max_tokens`). Разделы 2–4 сами не влезают — модель не зовётся (любой её
  ответ оборвался бы, а каждая попытка — полноразмерный платный запрос), ошибка
  «реестр и списки больше лимита вывода модели памяти (≈ X из Y токенов):
  поднимите лимит/бюджет или почистите снимок вручную». Не влезает весь снимок,
  а разделы 2–4 влезают — сначала сжатие хроники с арками, потом слияние; не
  помогло — ошибка «снимок больше лимита вывода модели памяти даже после сжатия
  хроники …».

### Ручные команды (вкладка «Память»)

Блок «🧠 Мастер-память этого чата» виден, когда открыт чат, и стоит над общими
настройками памяти.

- **Статус**: «Снимок 4 200 / 12 000 ток. · учтено до #812 · ждут сжатия 37»
  (метки не слипаются и на ширине 375 px переносятся целиком). Снимка нет —
  «Снимка нет: окно пропускает историю целиком». Пересказ старой схемы — пометка
  «старая схема — пересоберите». Есть буфер ручной пересборки, а задания нет —
  «Пересборка прервана на #400. [Продолжить]»; у сводки до 2.4.0 — «Старая
  сводка переводится в новую схему: готово до #N».
- **Предупреждения** — под строкой статуса, с «⚠», не больше пяти строк (дальше
  «…и ещё N предупреждений»): `snapshot.warnings` всегда, `job.warnings` — когда
  задание кончилось. Здесь видно «модель потеряла N записей — возвращены…»,
  «снимок превышает бюджет…», «сжатие … — оставлен прежний снимок», «сжимать
  нечего — весь чат в окне» и предупреждение о лимите вывода модели.
- **Сбой ежеходного обновления** (`snapshot.last_error`) — строка «⚠ Память не
  обновилась: <текст ошибки>. Следующая попытка — после ЧЧ:ММ или кнопкой
  «Догнать».» (`retry_after` прошёл или его нет — «со следующим ходом»). Пока
  идёт ручное задание, строка скрыта: оно само и есть попытка.
- **Пересобрать с нуля** (`mode: "rebuild"`). Подтверждение называет оценку:
  ⌈(сообщений в чате − окно) / размер пакета⌉ платных запросов к модели сводки
  «плюс факты — только там, где их ещё нет». Снимок собирается с нуля в буфер
  `meta.rebuild = {content, last_message_id, manual: true, started_at,
  batch_size}`, а старый снимок до конца работает в контексте, и окно верит его
  указателю. В конце — атомарная подмена (`updated_by: "rebuild"`), даже если
  хвост короче `summary_every`. Правки старого снимка, сделанные за время
  пересборки, при подмене теряются. Записи снимка не было — пакеты сразу пишутся
  в живой снимок. Старше окна нет ничего — старый снимок остаётся, а задание
  завершается `done` с `processed: 0` и предупреждением «пересборка не нашла
  сообщений старше окна — прежний снимок оставлен».
- **Продолжить** (`resume: true`) — продолжить буфер с его указателя (пометка
  «остановлена» с него снимается). Буфер пересборки, прерванной ошибкой или
  перезапуском сервера, продолжают и ежеходные проходы — так пересборка
  переживает перезапуск; остановленный кнопкой — только «Продолжить».
- **Догнать** (`mode: "catchup"`, кнопка активна, если что-то ждёт сжатия) —
  свернуть весь бэклог в цель записи: порог 1 сообщение вместо `summary_every`,
  без лимита шести пакетов. Цель — живой снимок, а если есть незаконченная
  (не остановленная) пересборка или сводка до 2.4.0 — её буфер, с подменой
  живого снимка, когда буфер догонит чат. Больше трёх пакетов — подтверждение
  «Догнать память? Примерно K пакетов = K платных запросов к модели сводки…».
  Всё старше окна уже в снимке — `done` с `processed: 0` и «догонять нечего —
  всё, что старше окна, уже в снимке»; весь чат в окне — «сжимать нечего — весь
  чат в окне».
- **Остановить** — начатый запрос к модели доводится, пауза между запросами и
  пауза перед повтором обрываются сразу, новых запросов нет. Слитый пакет
  сохраняется (его сжатие хроники пропускается, факты доизвлечёт следующий
  пакет); задание из очереди снимается сразу. Буфер остановленной пересборки
  помечается `meta.rebuild.paused`: ежеходные проходы его НЕ продолжают, а пишут
  в живой снимок — раньше «Остановить» было лишь паузой за чужой счёт (до шести
  платных слияний за ход в буфер, живой снимок не обновлялся, а в конце буфер
  сам его подменял). Буфер ждёт «Продолжить»; его заменяет новая «Пересобрать
  с нуля» (буфер начинается заново), а убирает «Сбросить память». Живой снимок
  тем временем обновляется как обычно.
- **Экспорт .md** — снимок файлом `memory-<название чата>-<id>.md`: шапка
  (персонаж, сообщений в чате, учтено до, размер и бюджет, схема, время выгрузки),
  сам снимок и приложение «атомарные факты».
- **Сбросить память** (`btn-danger`, с подтверждением) — остановить задание и
  идущий ежеходный проход (оба останавливаются после текущего запроса к модели,
  паузы обрываются сразу), дождаться их и удалить снимок (с буфером) и все факты
  чата. Сообщения остаются. Указатель становится 0, и окно ничего не выбрасывает,
  пока память не соберётся заново.
- **Параметры**: «Размер пакета» (1–200), «Пауза между запросами, мс» (0–60000),
  «Бюджет снимка, токенов» (поле — 1000–40 000, «не больше лимита вывода модели
  памяти»; сервер принимает до 200 000). Если модель памяти успевает написать
  меньше (`settings.max_snapshot_tokens`), под полем — «⚠ Модель памяти выдаёт
  не больше ≈N токенов снимка — уменьшите бюджет». Пока человек не поменял поле
  сам, оно показывает действующее значение сервера (из `.env`) и в настройки
  `ui` не пишется — умолчания `.env` не затеняются.

На чат — одно задание, на процесс — тоже одно: задания других чатов ждут в
очереди (`queued`), пока не кончится идущее (пауза между запросами действует
внутри одного прогона и иначе не защищала бы общий ключ провайдера). Задание,
ждущее очереди, свой чат не занимает — ежеходные проходы в нём идут. Замок чата
общий с ежеходным проходом: пока идёт задание, проходы после ходов пропускаются,
а задание ждёт (`queued`) конца уже начатого прохода. Реестр заданий живёт в
памяти процесса; завершённое задание остаётся в нём до следующего запуска
(вкладка видит, чем кончилось), удаление чата убирает его сразу
(`forget_job`). Выключатель «Авто-сводка сюжета» на задания не влияет.

Ошибка задания — статус `error` и русский текст: сбой провайдера после повторов
(«Провайдер ограничил частоту запросов: …», «Доступ к модели отклонён — проверьте
ключ API и права: …»), обрыв лимитом вывода («Ответ модели упёрся в лимит длины
вывода: …», «реестр и списки больше лимита вывода модели памяти …»), «модель
вернула снимок не по схеме: …», «переписка менялась во время сжатия, повторите»,
«чат удалён — памяти больше некуда записываться». Те же тексты — у
`snapshot.last_error` ежеходного прохода. Записанные пакеты и буфер остаются —
задание можно продолжить.

### Статус и прогресс

`GET /api/sessions/{id}/memory` (см. [API.md](API.md)) отдаёт:

- `job` — последнее задание или `null`: `mode`, `status` (`queued`, `running`,
  `done`, `error`, `cancelled`), `processed`/`total`, `batches`, `state_tokens`
  (размер цели прогона — у пересборки буфера), `phase`, `retry_in_s`, `line`,
  `error`, `warnings`, `snapshot_tokens` (размер живого снимка после задания —
  для итога; `null`, пока задание идёт или если упало), `queued_at`,
  `started_at` (переход в `running`), `finished_at`;
- `snapshot` — `exists`, `tokens` (по тексту: снимок могли поправить руками),
  `budget`, `covered_upto`, `schema`, `structured`, `updated_at`, `over_budget`,
  `warnings` (сохранённые с последней записью плюс предупреждение о лимите
  вывода модели памяти), `last_error` (`{message, kind, at, failures}` —
  сбой ежеходного прохода — или `null`), `retry_after` (ISO UTC: не раньше чего
  ежеходный проход попробует снова; `null` — ошибки нет);
- `staging` — буфер пересборки или `null`: `last_message_id`, `tokens`, `manual`,
  `started_at`, `paused` (остановлен кнопкой и ждёт «Продолжить»). У сводки до
  2.4.0 он есть и без явного буфера (`manual: false`): она пересобирается
  неявно, с нуля;
- `backlog` — `pending` (сообщения старше окна, ещё не учтённые целью записи — при
  пересборке буфером; у остановленной пересборки цель — живой снимок), `window`,
  `messages_total`;
- `facts.count`; `settings` — действующие `batch_size`, `delay_ms`,
  `snapshot_tokens` и `max_snapshot_tokens` — наибольший бюджет снимка, который
  модель памяти успевает написать (`null` — LiteLLM её лимит не знает).

Строка прогресса `line` — `[Обработано 140/800 сообщений | Сжато до 4 200
токенов]` (тысячи — через неразрывный пробел). Фазы `phase`: `merge` (слияние),
`compact` (сжатие хроники), `wait` (пауза между запросами), `retry` (повтор через
`retry_in_s` с), `done`. Вкладка показывает полосу, строку и под ней номер
пакета и фазу: при `merge`/`retry`/`compact` — номер пакета, который сейчас
считается («Пакет 8 · сжатие хроники», «Пакет 8 · сбой API — повтор через 3 с»),
при `wait` — записанные («После пакета 7 · пауза между запросами»); и кнопку
«Остановить». Прогресс объявляется скринридеру (`aria-live`), фокус после
старта, сброса и конца задания остаётся на «Остановить» или заголовке блока.
Пока задание `queued`/`running`, статус опрашивается раз в 1,5 с; по
завершении — тост и перечитка монитора токенов и записей памяти:

- `done` — «Память пересобрана: 800 сообщений → 11 900 токенов» (`rebuild`) или
  «Память догнала чат: …» (`catchup`); токены — `job.snapshot_tokens`, живой
  снимок после задания. Есть предупреждения — «(есть предупреждения — см.
  панель)». `processed: 0` — текст первого предупреждения («Пересборка не нашла
  сообщений старше окна — прежний снимок оставлен», «Сжимать нечего — весь чат
  в окне»), а не «0 сообщений → 0 токенов», читавшееся как стёртая память;
- `cancelled` — «Пересборка остановлена, готовое сохранено» / ««Догнать»
  остановлено, готовое сохранено»; до первого пакета — «Задание памяти
  остановлено до первого пакета — память не менялась»;
- `error` — «⚠ Память: <текст ошибки>».

Снимок в списке записей памяти (категория `summary`) свёрнут: «Показать снимок
(N строк)», развёрнутый — с переводами строк как есть.

### Монитор токенов

`GET /api/sessions/{id}/context` отдаёт `report.tiers` — из чего складывается ход:

- `system` — Tier 1: системный промпт, база знаний целиком (текст и медиа),
  аватары и статичные блоки хвоста (манифест файлов, внешность, веб, время,
  Author's Note, якорь, post-history, глобальные инструкции, фокус);
- `memory` — Tier 2: блок мастер-снимка и блок вспомненных фактов;
- `window` — Tier 3: история после окна и обрезки по бюджету;
- `current` — текущее сообщение (в инспекторе 0: следующий ход ещё не написан);
- `total`, `budget` (бюджет хода), `model_limit` (`MODEL_CONTEXT_LIMIT`,
  1 000 000), `pct_budget`, `pct_limit` — доли в процентах;
- `window_messages` (сколько сообщений идёт дословно), `dropped_messages` (сколько
  выбросило окно — они только в снимке), `trimmed_messages` (сколько срезал бюджет
  уже после окна).

Чтобы разделить хвост по уровням, каждый его блок получил ключ (`snapshot`,
`recalled`, `manifest`, `appearance`, `web`, `time`, `author_note`, `anchor`,
`post_history`, `global`, `focus`) — он виден в `report.tail[i].key`. К памяти
относятся только `snapshot` и `recalled`; новый блок хвоста без правки монитора
попадёт в Tier 1, а не выпадет из суммы.

**Снимок входит в бюджет хода.** Всё, что не зависит от обрезки истории, —
системный промпт, аватары, база знаний (текст и медиа), блок снимка, статичный
хвост и текущее сообщение — собирается до неё, и его вес резервируется: история
режется под остаток (`stable_trim_start`, ступенями по 16 сообщений, чтобы не
сбивать кэш промпта). Раньше резерв считал только системный промпт и реплику, и
снимок с базой знаний шли сверх бюджета: при бюджете 30 000 в модель уходило
34–41 тыс. токенов. Не резервируются только блоки, которые зависят от самой
обрезки: вспомненные факты (не больше пяти по 300 символов, ≈ 800 токенов, и
лишь на ходах, где что-то вспомнилось — резерв по потолку отнимал бы их у
истории каждый ход) и одна строка манифеста файлов. Это и есть возможный
перерасход бюджета.

**Групповые чаты** монитор не считает: `tiers: null` и `tiers_unavailable:
"group"`. Ход группы собирает `group_chat.build_group_messages` — окна нет,
транскрипт идёт целиком, снимок в системном промпте, отдельный запрос на каждого
отвечающего, а монитор считал бы конвейер личного чата и занижал цену хода в
разы. Вкладка и инспектор пишут «В групповых чатах монитор уровней не
считается: память собирается иначе, окна нет.»

Во вкладке «Память» и в инспекторе хода — одна и та же трёхсегментная полоса:
«Системный промпт и якоря», «Мастер-снимок и факты», «Окно (N сообщений)» — с
числами в подписях (прогресс не только цветом). Во вкладке под ней ещё строки
«из бюджета хода 200 000 (35%)» и «из лимита модели 1 000 000 (7%)»; в
инспекторе доля от бюджета — в его шапке («N токенов из M · X% окна»). Монитор
пересчитывается при открытии вкладки, после задания и сброса, после смены окна,
бюджета снимка и бюджета хода.

### Настройки

`.env` (`backend/config.py`, образец — `.env.example`):

| Имя | По умолчанию | Что задаёт |
|---|---|---|
| `MEMORY_BATCH_SIZE` | 20 | сообщений в пакете |
| `MEMORY_BATCH_CHARS` | 80 000 | потолок пакета в символах (не ниже 2000) |
| `MEMORY_DELAY_MS` | 1500 | пауза между запросами памяти, мс |
| `MEMORY_SNAPSHOT_TOKENS` | 12 000 | бюджет снимка, токенов |
| `MEMORY_MAX_RETRIES` | 4 | повторов запроса при сбое провайдера |
| `MEMORY_TEMPERATURE` | 0.2 | температура служебных вызовов памяти |
| `MEMORY_MAX_BATCHES_PER_TURN` | 6 | пакетов ежеходного прохода за ход |
| `MODEL_CONTEXT_LIMIT` | 1 000 000 | лимит контекста модели для монитора токенов |

Вкладка «Память» (глобальные ключи `ui`, как остальные настройки памяти):
`memory_window` (активное окно, по умолчанию 50, 0–1000), `memory_batch`
(«Размер пакета», 1–200), `memory_delay_ms` («Пауза между запросами, мс»,
0–60000), `memory_snapshot_tokens` («Бюджет снимка, токенов»: сервер принимает
1000–200000, поле вкладки — до 40 000). Значения из `ui` важнее `.env`, а размер
пакета и пауза, переданные при запуске задания, — важнее `ui`. Ключа в `ui` нет,
пока человек сам не поменял поле: до тех пор действует `.env`. Флаги разовых
миграций интерфейса: `memory_defaults_v: 2` (окно 20 → 50) и `ctx_budget_v: 2`
(сохранённый бюджет хода 1 000 000 → 200 000 — один раз; выбранный после этого
вручную 1 млн больше не сбрасывается).

**Лимит вывода модели памяти.** Снимок переписывается целиком, и потолок вывода —
`max(DEFAULT_MAX_TOKENS, round(бюджет снимка × 1,4) + 1024)`, 17 824 токена при
бюджете 12 000. Если LiteLLM знает модель памяти (`summary_model`, пусто —
модель чата; через прокси имя пробуется и без префикса `litellm_proxy/`),
`max_tokens` прижимается к её `max_output_tokens`, а рабочий бюджет снимка — к
наибольшему, который она успевает написать: ⌊(лимит − 1024) / 1,4⌋. У `gpt-4o`
(лимит вывода 16 384) это ≈ 10 971 токен: без прижатия каждый запрос с 17 824
получал 400, и снимок не собирался никогда. Статус отдаёт это число в
`settings.max_snapshot_tokens`, а если бюджет больше — предупреждение в
`snapshot.warnings`. Модель LiteLLM не знает (псевдоним прокси) и провайдер
отверг `max_tokens` (400 со словом `max_tokens`/`maxOutputTokens`) — один
повтор с `DEFAULT_MAX_TOKENS` и предупреждение «модель памяти не приняла
max_tokens=…»; дальше в прогоне запросы идут сразу с ним, и большой снимок
оборвётся — уменьшите бюджет или выберите модель памяти с длинным выводом.

Обрыв лимитом, когда реестр и списки (разделы 2–4) сами больше лимита вывода,
уменьшением бюджета не лечится: бюджет сжимает только хронику. Тогда нужна
модель памяти с бо́льшим выводом или ручная чистка разделов 2–4 во вкладке
«Память».

### Стоимость

- **Постоянная, на каждом ходу.** Снимок до «Бюджета снимка» (12 000 токенов, а
  если разделы 2–4 переросли бюджет — больше) идёт в КАЖДЫЙ ход, в хвост, вне
  кэшируемого префикса. До 2.5.0 сводка была не длиннее 6000 символов (1,5–2,5
  тыс. токенов).
- **Постоянная, на каждом обновлении.** Раз в `summary_every` сообщений (10)
  модель памяти переписывает снимок ЦЕЛИКОМ: вход — промпт (≈ 1 600 токенов),
  снимок и пакет, вывод — весь снимок, до потолка вывода (17 824 при бюджете
  12 000). Сверху запрос фактов, а раз в несколько обновлений — сжатие хроники.
  Вывод на одно обновление вырос против 2.4.x в 5–10 раз.
- **Как снизить**: меньше «Бюджет снимка» (меньше и вход хода, и вывод
  обновления), реже `summary_every` (20 вместо 10 — вдвое меньше переписываний),
  быстрая и дешёвая `summary_model` во вкладке «Подключение».
- **Пересборка** — ⌈(сообщений − окно) / размер пакета⌉ запросов слияния и
  изредка сжатие хроники. Факты заново извлекаются только там, где их ещё нет:
  у чата с фактами пересборка их не запрашивает вовсе (плюс до одного запроса
  фактов на пакет, если фактов у чата нет — после «Сбросить память» или у сводки
  до 2.4.0). Чат на 1 050 сообщений при окне 50 и пакете 20 — около 50 запросов
  к `summary_model`.

## Деградация

Память не имеет права ронять ход:

- нет модели эмбеддингов → поиск по словам;
- эмбеддинг запроса не посчитался (ошибка, таймаут) → поиск по словам;
- векторы ещё досчитываются → поиск по словам;
- долгая память не собралась целиком (любое исключение в `_long_memory`) →
  модель получает всю историю, как до появления окна, без блока фактов;
- сбой фонового прохода (ошибка API после повторов, снимок не по схеме, обрыв
  лимитом вывода) → ход не затронут, указатель не двигается, ошибка — в
  `meta.last_error` и во вкладке «Память», следующий ежеходный проход — после
  паузы (10 мин, 20, 40… до 6 ч), «Догнать» — сразу;
- сбой извлечения фактов → снимок пакета остаётся, пропущенные сообщения
  доизвлечёт следующий пакет;
- сбой задания → статус «ошибка» с текстом причины; записанные пакеты и буфер
  пересборки остаются, старый снимок продолжает работать.

## Что видно в инспекторе промпта

`GET /api/sessions/{id}/context` отдаёт `report.memory`, `report.recalled` и
`report.tiers`; в UI это раздел «Память Horae: окно, хроника, факты» и полоса
уровней хода (см. «Монитор токенов»).

- `memory`: `window` (размер окна), `dropped` (сколько сообщений сжато в снимок
  и не идёт дословно), `covered_upto` (до какого сообщения доведён снимок),
  `facts_enabled`, `facts_mode` (`vector` — по смыслу, `lexical` — по словам,
  `off`), `facts_candidates` (сколько фактов у чата), `facts_backfilling`
  (векторы ещё досчитываются), `error: true` — память на этом ходу не собралась.
- `recalled`: отобранные факты `{content, similarity, score}`; пустой список —
  блок `[HORAE RECALLED MEMORY]` в модель не ушёл.
- `tail[i].key`: какой это блок хвоста (`snapshot`, `recalled`, `anchor`, …).

## Известные ограничения

- Telegram-чаты сводку не запускают: окно там ничего не выбрасывает, фактов нет.
- Правка или удаление сообщения в середине уже учтённой части не пересчитывает
  снимок и факты из него. Пересчитать — «Пересобрать с нуля» (платно).
- `source_message_id` факта — последнее сообщение его пакета: факт из начала
  пакета, который кончается внутри окна, придерживается, пока окно не уйдёт
  дальше (всё это время его покрывает снимок).
- Векторный поиск — на чистом Python (numpy нет): ~3 400 фактов × 1 536
  измерений стоят 0,1–0,3 с на ход при тёплом кэше.
- Сообщение длиннее бюджета пакета (`MEMORY_BATCH_CHARS`, 80 000 символов)
  сворачивается началом и концом, а указатель считает его учтённым целиком: когда
  оно выйдет из окна, его середина останется только в фактах, извлечённых из тех
  же начала и конца. Для больших документов есть база знаний.
- Разделы 2–4 снимка автоматически не сжимаются. Если бюджет превышают они сами,
  снимок остаётся больше бюджета (статус предупреждает): сократить можно правкой
  записи во вкладке «Память» или увеличив бюджет. Если они переросли лимит
  вывода модели памяти, обновление останавливается с ошибкой «реестр и списки
  больше лимита вывода…» — нужна модель с бо́льшим выводом или ручная чистка.
- Снимок в хвосте не попадает в кэш промпта провайдера ни на одном ходу (он
  стоит после истории): до 12 000 токенов по полной цене на каждом ходу.
  Осознанный выбор: у конца снимок сильнее влияет на ответ.
- Блок вспомненных фактов не резервируется в бюджете хода (см. «Монитор
  токенов»): ход с фактами может превысить бюджет на их размер, до ≈ 800 токенов.
- Ручная правка снимка не сверяется с работающим прогоном: пакет, который модель
  уже считает, её перезапишет, а подмена в конце пересборки заменит живой снимок
  буфером целиком. Интерфейс правку в это время не блокирует; править стоит, когда
  задания и буфера пересборки нет (подробнее — «Свёртка пакетами»).
- Страж узнаёт записи по формату схемы («- » у края строки, подсписки `### …`).
  Если модель оформила раздел иначе (например, «**Имя**» с вложенным списком без
  отступа), выпавшая запись может не вернуться.
- Задания живут в памяти процесса: перезапуск сервера теряет их статус и
  прогресс, постоянной очереди нет. Сделанное уже в БД; прерванную перезапуском
  пересборку продолжают «Продолжить» или ежеходные проходы, остановленную
  кнопкой — только «Продолжить». Ошибка ежеходного прохода чата, у которого
  записи снимка ещё нет, тоже живёт в памяти процесса: после перезапуска будет
  одна попытка без паузы.
- Пересборка платная: ⌈(сообщений − окно) / размер пакета⌉ запросов слияния и
  изредка сжатие хроники; факты — только там, где их ещё нет (см. «Стоимость»).
- Задания памяти идут по одному на процесс: пересборка большого чата держит в
  очереди «Пересобрать» и «Догнать» остальных чатов (их ежеходные проходы идут).
- Групповые чаты: снимок и факты собираются, но активного окна нет — история
  режется только бюджетом, а факты последних `DEFAULT_WINDOW` (50) сообщений
  группа не вспоминает, какое бы окно ни стояло в настройках. Снимок идёт там не
  блоком хвоста, а в системный промпт, как любая `always_on`-запись: строкой
  `- 📜 Память чата (авто): …` в блоке `[Memory & World State]`. Монитор уровней
  для групп не считается (`tiers: null`, `tiers_unavailable: "group"`).
