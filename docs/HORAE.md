# Подсистема памяти Horae

Horae — система памяти/контекста. Она совмещает две идеи SillyTavern:

- **World Info** — записи срабатывают, когда в недавнем тексте встречаются их
  **ключевые слова** (`keywords`).
- **Снимки состояния** — записи с `always_on=True` подмешиваются **всегда** (инвентарь,
  скрытые характеристики, текущее положение сюжета, описание сцены).

Плюс автоматическая **долгая память** для длинных чатов (см. «Три слоя памяти»
ниже): активное окно дословной переписки, скользящая хроника чата и атомарные
факты, которые вспоминаются по смыслу текущей реплики.

Код: `backend/horae_memory.py` (сборка контекста), `backend/horae_recall.py`
(окно, факты, поиск), `backend/main.py::_maybe_update_summary` (фоновая сводка).
Модели: `HoraeEntry`, `HoraeFact` (см. [DATA_MODEL.md](DATA_MODEL.md)).

## Области видимости записи

Запись Horae может быть привязана так:

| `session_id` | `character_id` | Смысл |
|:---:|:---:|---|
| NULL | NULL | **Глобальный лор мира** — виден во всех чатах (и всем пользователям) |
| задан | — | **Память конкретного чата** (приватная для владельца чата) |
| — | задан | **Лорбук персонажа** — применяется в чатах с этим персонажем |

В UI у каждой записи показывается тег области (🌐 глоб. / 💬 чат / 🎭 перс.).

## Как собирается контекст

`assemble_context(...)` — **чистая** функция (без БД и сети, поэтому легко покрывается
юнит-тестами `tests/test_horae_memory.py`). Порядок:

1. **Триггеры.** По тексту текущего сообщения + хвоста истории ищутся записи, чьи
   `keywords` встретились (`_scan_text_for_triggers`). `always_on`-записи добавляются
   безусловно.
2. **Системный промпт (начало)** = паспорт персонажа (`system_prompt/description/
   personality/scenario/mes_example`) + блок персоны пользователя + блок сработавших
   записей Horae (по `priority`, КРОМЕ авто-сводки) + `BEHAVIOR_GUIDE` (роль, работа
   с файлами, анти-выдумки) + `STYLE_GUIDE` (портативная разметка).
2b. **Переинъекция в КОНЕЦ** (сильнейшая позиция — recency bias). Чтобы характер не
   «плыл» и память реально влияла в длинном окне, прямо перед репликой пользователя
   добавляются системные блоки: `[ХРОНИКА И СОСТОЯНИЕ ЧАТА]` (авто-сводка Horae),
   `[HORAE RECALLED MEMORY: …]` (вспомненные факты, если есть), манифест
   приложенных файлов, инструкция веб-поиска (если включён), время пользователя,
   Author's Note, **якорь характера** (`_render_char_anchor`) и, в самом конце,
   **Post-History Instructions** персонажа (SillyTavern «jailbreak»/UJB).
3. **Бюджет токенов.** Несжимаемая часть — системный промпт + текущее сообщение.
   История добавляется с конца (свежие важнее), пока хватает окна контекста:
   `params.context_tokens` из UI (Генерация → «Окно контекста») либо
   `CONTEXT_TOKEN_BUDGET` из .env (по умолчанию 1 000 000 — максимум Gemini).
   Вложения истории (фото/аудио/видео) пересылаются модели заново: по умолчанию
   ВСЕ (полная память), опционально — до N МБ на ход (`history_files_mb` из UI
   «Файлы в памяти диалога» / `HISTORY_FILES_MB` из .env; не влезшие заменяются
   пометкой `[видео: имя]`). Данные достаются точечно из blob-таблицы.
4. **Author's Note** добавляется отдельным system-сообщением в самый конец контекста —
   так у заметки максимальное влияние на ответ.
5. **Аватары** (если включено `send_avatars`) — внешность персонажа и пользователя
   подмешиваются как картинки.

`build_context_from_db(...)` — обёртка: читает персонажа, персону, историю и записи
Horae (свои + лорбук персонажа, с учётом доступа), применяет долгую память
(`_long_memory`: срез активного окна + поиск фактов) и зовёт `assemble_context`.
Вызывающий, который передаёт историю сам (regenerate/continue/retry), передаёт и
`history_ids`; без них id не угадываются — окно ничего не выбрасывает и факты не
отсеиваются.

## Приватность

`GET /api/horae` и операции над записями скоупятся по доступу (`_can_access_horae` в
`main.py`): глобальный лор виден всем; приватная память чата и лорбук персонажа — только
владельцу, админу и соавтору расшаренного чата. Регрессия закреплена тестом
`tests/test_horae_privacy.py`.

## Откуда берутся записи

- Вручную в UI (вкладка «Память Horae»): заголовок, содержимое, ключевые слова,
  категория, `always_on`, область (глобально / только этот чат).
- При **импорте чата** (нативном или SillyTavern) — снимок состояния и хронология
  событий (см. [IMPORT_EXPORT.md](IMPORT_EXPORT.md)).
- При **импорте карточки персонажа** — лорбук (`character_book`) → записи персонажа.


## Три слоя памяти

Проблема: в длинном чате (вплоть до ~1M токенов) модель получала всю переписку,
насколько хватало бюджета, и тонула в ней (Context Dilution). Факты и хронология
из начала размывались сотнями реплик, а не влезшее в бюджет просто отрезалось.
Поэтому история перед сборкой контекста проходит конвейер из трёх слоёв.

### 1. Активное окно (дословно)

Последние `DEFAULT_WINDOW = 20` сообщений идут в модель без изменений
(`horae_recall.window_start`). Всё старше выбрасывается, **но только если уже
учтено сводкой** (id сообщения ≤ указателя «учтено до»): пока сводка догоняет
длинный или импортированный чат, модель видит историю целиком. Отбрасывается
только ведущий непрерывный отрезок учтённых сообщений; первое неучтённое или
сообщение без id останавливает срез.

Граница окна двигается шагом `WINDOW_STEP = 4`, а не на каждом ходу: иначе
каждый ход сдвигал бы начало промпта и ломал кэш промпта провайдера. Поэтому
дословно идут 20–23 сообщения.

Размер окна — вкладка «Память» → «Активное окно» (`/settings/ui`, ключ
`memory_window`; любое целое 0–1000, кнопки 20/40/80/150, `0` = окно выключено,
история целиком). Указатель
берётся только у сводки, которая реально идёт в контекст (`enabled` и
`always_on`): если снять с неё «всегда», окно ничего не выбрасывает.

### 2. Хроника (скользящая сводка)

После каждого хода запускается фоновая задача `main.py::_maybe_update_summary`.
Когда старше активного окна накопилось `summary_every` новых сообщений (по
умолчанию 10, `AUTO_SUMMARY_EVERY` в .env; в UI — 6/10/20), модель сливает СТАРУЮ
сводку с новыми событиями в структурированный конспект: текущее состояние
сюжета и цель; ключевые решения и события; персонажи — статусы и инвентарь;
локации и мир; незакрытые линии.

- Сообщения из активного окна в сводку не берутся: свайпы, «Продолжить» и правки
  свежих ответов попадают в память уже в окончательном виде.
- Бэклог режется на куски до `_SUMMARY_CHUNK_CHARS = 24000` символов, до
  `_SUMMARY_MAX_CHUNKS = 6` проходов за запуск; сообщение идёт в кусок целиком,
  а длиннее куска — началом и концом (середина пропускается с пометкой): целиком
  оно превысило бы окно быстрой модели, и сводка падала бы на каждом ходу.
  Указатель двигается только за тем, что модель действительно видела.
- Фоновые вызовы идут на `summary_model` из подключения (пусто = модель чата), но
  остаются служебными — `params=None`, фильтры безопасности выключены. Иначе на
  жёстком ролевом эпизоде провайдер блокировал сводку, и память молча замирала.
- Результат — запись Horae этого чата: категория `summary`, заголовок
  «📜 Память чата (авто)», `always_on=True`, `priority=50`, ключевое слово
  `__auto__`. Указатель «учтено до» хранится в `meta.last_message_id` вместе с
  версией формата `meta.v = 2` (`horae_recall.SUMMARY_FORMAT`). Запись видна во
  вкладке «Память», её можно править руками или удалить (сводка начнётся заново).
- **Сводка до 2.4.0 пересобирается.** Старый сводчик резал реплики до 1500
  символов, а бэклог — до первых 24 000, но ставил указатель на последнее
  сообщение. Окно верит только указателю с `v = 2`
  (`horae_recall.trusted_pointer`), поэтому у старой сводки оно не выбрасывает
  ничего — история идёт как до обновления. Новый сводчик пересобирает память с
  нуля в `meta.rebuild = {content, last_message_id}` (заодно извлекая факты из
  всей старой истории), а в контекст до конца пересборки идёт старая сводка.
  Подмена (`_adopt_summary`) — только когда пересборка догнала бэклог (остаток
  меньше `summary_every`); по указателю старой сводки не подменяем — у сводки
  из импорта его нет. Разово это стоит пересказа всей переписки чата — задайте
  дешёвую `summary_model` до обновления. Ручные правки старой авто-сводки в
  новую не переносятся: храните свои заметки отдельной записью памяти.
- Факты извлекаются только из сообщений новее `max(source_message_id)` фактов
  чата: сводка, начатая заново (удалили запись, пересборка), не плодит дубли.
- Перед записью прохода кусок сверяется с чатом: если его сообщения переписали
  или удалили, пока модель считала (а id занял новый ответ), проход не
  записывается и повторится — иначе указатель лёг бы на невиданный текст.
- В контекст хроника идёт блоком `[ХРОНИКА И СОСТОЯНИЕ ЧАТА]` у конца, рядом с
  репликой пользователя: когда окно отрезает старую переписку, это единственное,
  что от неё остаётся.
- Удалили свежие сообщения — `_clamp_summary_pointer` прижимает указатель к
  последнему оставшемуся сообщению (а не в ноль, что заставляло пересказывать
  весь чат заново) и удаляет факты из удалённого. id в SQLite переиспользуются,
  поэтому без этого новый ответ с «чужим» id считался бы уже учтённым.
- Выключатель: «Память» → «Авто-сводка сюжета» (`auto_summary`). Без сводки
  указатель не растёт, и окно ничего не выбрасывает.

### 3. Атомарные факты (`backend/horae_recall.py`, таблица `horae_facts`)

В тот же фоновый проход модель выписывает из куска переписки атомарные факты
(`FACTS_PROMPT`): одно утверждение, имена вместо местоимений, только то, что прямо
сказано, до `MAX_FACTS_PER_CHUNK = 20` фактов по `MAX_FACT_CHARS = 300` символов.
Индексируются именно факты, а не сырые реплики: вектор абзаца ролевого чата
«про всё сразу» и похож на всё понемногу.

`store_facts` отбрасывает точные повторы, а при заданной модели эмбеддингов — и
почти повторы (косинус ≥ `DUP_COSINE = 0.95` среди последних 400 векторов).
Сбой записи фактов не откатывает уже сохранённую сводку.

**Поиск** (`recall`, на каждом ходу). Запрос — реплика пользователя; хвост
разговора (две последние реплики) идёт отдельно и сам по себе факт не вспоминает,
только помогает с «а что с ним?».

- **По смыслу**, если задана `embedding_model`: косинус с порогом
  `SIM_THRESHOLD = 0.75`. Включается, только когда векторы текущей модели есть
  у ≥ 95% фактов (`VECTOR_COVERAGE`); до тех пор — поиск по словам, а векторы
  досчитываются после каждого хода пачками по 50 (не больше 10 пачек за раз).
- **По словам** (режим по умолчанию): основы слов с учётом падежей и глагольных
  приставок, IDF по фактам этого чата, вес `ENTITY_BOOST = 2.5` для имён
  (слово с заглавной внутри предложения), порог `LEXICAL_THRESHOLD = 0.2`.
  Слово, которое есть в ≥ 25% фактов чата (и не меньше чем в трёх), само по себе
  совпадением не считается — иначе «ок» или «иду дальше» вспоминали бы факты про
  главных героев на каждом ходу. Совпадения только с хвостом весят 0,3.
- Порог применяется к сходству, ранжирование — по «сходство × свежесть», где
  свежесть = 0,5 + 0,5 · 0,5^(возраст / 300): полураспад 300 сообщений ЭТОГО
  чата, пол 0,5 — старые факты ослабляются, но не обнуляются.
- В контекст идут не больше `TOP_K = 5` фактов, и только из сообщений, которых
  модель не видит дословно (отсев — после обрезки истории по бюджету, так что
  при `memory_window = 0` факты из срезанного бюджетом тоже вспоминаются).
  Блок `[HORAE RECALLED MEMORY: …]` стоит у конца, факты — в порядке чата.
  **Нет похожих — нет и блока**: пустой или натянутый блок памяти модель охотно
  «дополняет» выдумкой.

Эмбеддинги считает `llm_gateway.embed` через тот же маршрут, что и чат (прокси
или напрямую), с таймаутом 10 с; расход пишется в статистику как `embedding`.
Выключатель фактов: «Память» → «Факты» (`horae_facts`, выключены только явным
`false`). Групповые чаты тоже получают блок фактов (`group_chat._group_recalled`),
но активного окна у них нет — история там режется только бюджетом.

### Деградация

Память не имеет права ронять ход:

- нет модели эмбеддингов → поиск по словам;
- эмбеддинг запроса не посчитался (ошибка, таймаут) → поиск по словам;
- векторы ещё досчитываются → поиск по словам;
- долгая память не собралась целиком (любое исключение в `_long_memory`) →
  модель получает всю историю, как до появления окна, без блока фактов;
- сбой фоновой сводки или извлечения фактов → ход не затронут, указатель не
  двигается, следующий проход повторит попытку.

### Что видно в инспекторе промпта

`GET /api/sessions/{id}/context` отдаёт `report.memory` и `report.recalled`;
в UI это раздел «Память Horae: окно, хроника, факты».

- `memory`: `window` (размер окна), `dropped` (сколько сообщений сжато в хронику
  и не идёт дословно), `covered_upto` (до какого сообщения доведена сводка),
  `facts_enabled`, `facts_mode` (`vector` — по смыслу, `lexical` — по словам,
  `off`), `facts_candidates` (сколько фактов у чата), `facts_backfilling`
  (векторы ещё досчитываются), `error: true` — память на этом ходу не собралась.
- `recalled`: отобранные факты `{content, similarity, score}`; пустой список —
  блок `[HORAE RECALLED MEMORY]` в модель не ушёл.

### Известные ограничения

- Telegram-чаты сводку не запускают: окно там ничего не выбрасывает, фактов нет.
- Правка или удаление сообщения в середине уже учтённой части не пересчитывает
  сводку и факты из него.
- `source_message_id` факта — последнее сообщение его куска: факт из начала
  куска, который кончается внутри окна, придерживается, пока окно не уйдёт
  дальше (всё это время его покрывает хроника).
- Векторный поиск — на чистом Python (numpy нет): ~3 400 фактов × 1 536
  измерений стоят 0,1–0,3 с на ход при тёплом кэше.
- Сообщение длиннее `_SUMMARY_CHUNK_CHARS` пересказывается началом и концом, а
  указатель считает его учтённым целиком: когда оно выйдет из окна, его середина
  останется только в фактах, извлечённых из тех же начала и конца. Для больших
  документов есть база знаний.
