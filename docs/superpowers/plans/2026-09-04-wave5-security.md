# Волна 5: Безопасность, изоляция и вынос секретов — план реализации

**Цель:** закрыть три вещи, которые мешают открывать доступ посторонним: чужая
переписка в панели отладки, снятые фильтры по умолчанию и секреты открытым
текстом в базе.

**Подход:** владелец отладочной записи проставляется контекстной переменной, а не
протаскиванием параметра через шесть мест вызова в шлюзе LLM. Секреты читаются из
окружения с приоритетом над базой, а не «вместо» неё: иначе уже сохранённые
значения победили бы, и перенос оказался бы бессмысленным.

**Ограничения:** без сборки и новых зависимостей (`pydantic-settings` уже есть).
WS/SSE, `_handoffStreaming`, `resumeSSE`, сторож стриминга и пульс сокета из
волны 4 не трогаются. Откат — ветка `wave5-security`, копии в `C:/Temp/claude/w5-*`.

**Спека:** отчёт «Редизайн TaleEngine», раздел «Что меняет слово „публично“».

## Глобальные ограничения

- Пользователь без роли администратора не должен получить НИ ОДНОЙ чужой записи
  отладки ни при каких параметрах запроса.
- Настройка безопасности меняется только для НОВЫХ профилей. Уже сохранённые
  параметры существующих пользователей не переписываются: тихо менять поведение
  работающей установки хуже, чем оставить как есть.
- Значение из окружения имеет приоритет над базой. Интерфейс обязан показывать,
  что секрет задан снаружи, и не делать вид, что его можно поменять из UI.
- Существующие секреты в базе НЕ стираются автоматически: это разрушительное
  действие, оно остаётся за владельцем и делается отдельной командой.

## Задача 1: Изоляция буфера отладки

**Файлы:** `backend/debug_log.py`, `backend/main.py`

**Что не так:** буфер один на всё приложение, а эндпоинты `/api/debug/log` вообще
не проверяют, кто спрашивает. В режиме аккаунтов туда валятся ходы всех
пользователей, и любой залогиненный видит чужую переписку в сводке сообщений.

**Почему контекстная переменная:** `log_request` зовут из `llm_gateway`, который
про пользователя ничего не знает и знать не должен. Протаскивать `owner_id` через
`stream_completion`, `complete` и три функции картинок означало бы менять их
сигнатуры и все места вызова ради служебного поля. `contextvars` копируется в
задачу при `asyncio.create_task`, поэтому фоновая генерация наследует владельца
автоматически.

- [ ] **Шаг 1.** В `debug_log` добавить `ContextVar` владельца, функцию
      `set_owner(user_id)` и запись `owner_id` в каждую строку лога.
- [ ] **Шаг 2.** `entries(owner_id, include_all=False)` возвращает только записи
      владельца; `include_all=True` разрешён только администратору и проверяется
      В ЭНДПОИНТЕ, а не в модуле лога.
- [ ] **Шаг 3.** `clear(owner_id, include_all)` — то же правило для очистки.
- [ ] **Шаг 4.** Эндпоинты `/api/debug/log` получают `Depends(current_user)`.
      Параметр `all=true` работает только для администратора, иначе игнорируется.
- [ ] **Шаг 5.** Владелец проставляется в тех местах, где начинается ход:
      WebSocket-обработчик и REST-пути генерации.
- [ ] **Шаг 6.** Поведенческая проверка: два пользователя, каждый видит только
      свои записи, админ видит обе, `all=true` от обычного пользователя не даёт
      чужого.

## Задача 2: Безопасный дефолт фильтрации

**Файлы:** `backend/schemas.py`, `frontend/app.js`, `frontend/styles.css`

**Что не так:** `disable_safety: bool = True` в схеме и в `data()` клиента.
Каждый новый пользователь получает снятые фильтры провайдера, при этом сам
интерфейс красит этот переключатель в цвет опасности. Два сигнала противоречат
друг другу: либо это опасно и не должно быть дефолтом, либо это дефолт и не
должно быть красным.

- [ ] **Шаг 1.** `disable_safety` по умолчанию `False` в схеме и в клиенте,
      `safety_preset` по умолчанию не `"off"`.
- [ ] **Шаг 2.** Убедиться, что уже сохранённые параметры существующих
      пользователей ЗАГРУЖАЮТСЯ поверх дефолта и не переписываются.
- [ ] **Шаг 3.** Ненавязчивая подсказка при первом старте: одноразовый тост
      «Включён стандартный режим фильтрации», с отметкой в localStorage.
- [ ] **Шаг 4.** Бейдж режима фильтрации во вкладке «Генерация» рядом с
      переключателем: видно текущее состояние без чтения абзаца.

## Задача 3: Секреты в окружении

**Файлы:** `backend/config.py`, `backend/admin_service.py`, `backend/main.py`,
`frontend/app.js`, `.env.example`, `scripts/scrub_secrets.py`

**Что не так:** пароль администратора, код доступа и токен Telegram-бота лежат в
таблице `app_settings` открытым текстом. Резервная копия базы, экспорт или чужой
доступ к файлу означают компрометацию всего сразу.

- [ ] **Шаг 1.** В `config.py` добавить `ADMIN_PASSWORD` и `ACCESS_CODE`
      (`TELEGRAM_BOT_TOKEN` уже есть).
- [ ] **Шаг 2.** В `admin_service` значение из окружения ПЕРЕКРЫВАЕТ значение из
      базы при чтении, и не даёт записать себя из интерфейса.
- [ ] **Шаг 3.** Эндпоинт статуса: какие секреты заданы окружением. Нужен, чтобы
      интерфейс не предлагал править то, что правится не там.
- [ ] **Шаг 4.** В интерфейсе поля таких секретов помечаются и блокируются.
- [ ] **Шаг 5.** `.env.example` пополняется новыми переменными с пояснением.
- [ ] **Шаг 6.** `scripts/scrub_secrets.py` — ручная очистка секретов из базы
      после переноса. Требует подтверждения, делает резервную копию, ничего не
      удаляет молча.
- [ ] **Шаг 7.** `.gitignore` с `*.sqlite3` коммитится.
